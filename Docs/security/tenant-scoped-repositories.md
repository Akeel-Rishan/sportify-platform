# Tenant-scoped Oracle repositories

The resolver mints two runtime-checked, immutable capabilities. A website context carries the mapped website, business and tenant identities. A member context carries the verified tenant, account and membership. The repositories reject omitted, copied and wrong-surface contexts before SQL, and require a mutation context to start a write transaction. Capabilities are for the current request. Background work needs its own approved scope and purpose.

| Access                  | Step 13 implementation                                                                                                                                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Private resource reads  | Find by scoped UUID, list with a 100-row limit, and count and sum capacity. Location joins match tenant, business and location.                                                                                                              |
| Private resource writes | Internal insert, rename, deactivate and delete primitives. Insert derives ownership through the scoped location, requires the sport to be enabled for that business and generates the resource UUID. Changes never assign a different owner. |
| Bulk status changes     | One statement takes 1–100 distinct bound UUIDs. If any requested ID is foreign or missing, the entire batch affects zero rows.                                                                                                               |
| Public display          | One named projection of business name and website page title. It rechecks slug, tenant, business, website and publication on every read.                                                                                                     |

Transactions use the shared Oracle callback and bind the tenant once for all reads and writes in that callback. The callback object exposes named methods and no connection or tenant override. SQL identifiers are from a fixed owner allowlist and generated numbered placeholders. IDs stay exact strings. Only one shared application schema is used; pooled sessions carry no tenant identity. The pool rejects nested connection acquisition within an active transaction, rolls back failures and releases the connection. [Connection pooling](../database/connection-pooling.md) · [node-oracledb transactions](https://node-oracledb.readthedocs.io/en/latest/user_guide/txn_management.html)

Mutations recheck verified account, active membership and active/trial tenant in the DML admission predicate. Oracle statement visibility permits a statement admitted before concurrent revocation to finish. A repository read already authorized by its request may also finish. The next request revalidates access. Booking and other sensitive transitions require their own locks, admission policies and role checks. The resource primitives have no production controller and do not establish when deleting or deactivating a real resource is permissible.

## SQL review and grants

Manual review and search covered SQL under the API, worker and shared packages. Registration is global identity and verification-token access plus a single tenant bootstrap transaction. The existing tenant role inserts derive IDs from that transaction. Session access is scoped to the global account and dashboard audience. Login/reset counters are operational and keyed to the approved source policy. Permission and sports reads are global reference access. The health probe uses the database dependency check. The worker's mail adapters have narrow eligibility views and purpose-bound references. There is no platform-admin data path. The new tenant resolver is the intentional lookup across tenant candidates before joining to membership or the published website. Every ordinary tenant-owned resource lookup and mutation is tenant-predicated in SQL. [Registration](../auth/registration.md) · [Server sessions](../auth/server-side-sessions.md) · [Mail delivery](../auth/email-verification.md)

No migration or application database grant is needed to land this foundation in source. The isolated harness grants its exact access matrix temporarily to the API identity, with column-level inserts and updates for resource data. It verifies denials for tenant reassignment, customers, audit, base sessions and migration history. Before any production controller is opened, review a minimal grant set for that specific feature, including opportunities for narrow read-only views. Test grants are scoped to `SPORTIFY_STEP13_TEST_OWNER`.
