# Host and proxy trust

The Nest Express adapter uses the HTTP/1.x Host field at the origin. It counts wire fields in Node's `rawHeaders` and requires exactly one Host. The Node parser still enforces its byte limit and handles HTTP field framing whitespace. Embedded whitespace is invalid in an authority. The middleware rejects requests exceeding 2,000 fields and preserves its ability to see a late duplicate. An upstream parser can reject malformed HTTP before Express assigns a request ID. [Node 22 HTTP parser and raw header API](https://nodejs.org/download/release/v22.22.0/docs/api/http.html)

Canonical authorities are `sportify.lk`, `app.sportify.lk`, `admin.sportify.lk` and one ASCII DNS label under `sportify.lk`. Hostname case is normalized. Ports are omitted or `443` on canonical hosts. Trailing dots, malformed or ambiguous authorities, Unicode/IDNA labels, nested subdomains and origin-replacement request targets are rejected. Tenant labels may contain lowercase letters, digits and interior hyphens, with 1–63 characters. `admin`, `api`, `dashboard`, `app` and `www` are unavailable as tenant labels. The existing database constraint reserves `admin`, `api` and `dashboard`; future provisioning must apply the full routing rule, including `app`, `www` and the IDNA exclusion. Unknown eligible-looking labels return a generic 404 when the authoritative mapping is absent. [Approved storage policy](../database/website-ownership.md)

Express proxy trust is disabled. `Forwarded`, `X-Forwarded-Host`, `X-Forwarded-Proto` and custom original-host fields have no routing authority even when they conflict with Host. Tenant selection headers are rejected. Session and registration source limits continue to use the socket peer. Browsers use the approved HTTPS dashboard origin and host-only cookies. The production API rejects account configuration for a different origin. [Express proxy trust](https://expressjs.com/en/guide/behind-proxies/) · [Browser security](../auth/browser-security.md)

## Local testing and configuration

- Direct development probes can use `http://127.0.0.1:4000/api/v1/health` when `PORT=4000`. `localhost` and `[::1]` are also allowed from a loopback peer. Tests can use ephemeral loopback probe ports.
- For a local Step 12 dashboard, use the exact `AUTH_DASHBOARD_ORIGIN` and its approved protocol/cookie settings. A local HTTP origin requires `AUTH_ALLOW_LOOPBACK_HTTP=true`. The local dashboard alias is recognized only from a loopback peer outside production. Tests can use a configured ASCII `.test` dashboard from loopback.
- To exercise production-shaped authorities over local HTTP, send an explicit Host via `curl.exe -H "Host: app.sportify.lk" http://127.0.0.1:4000/api/v1/health`. Requests to alternate hosts are tested by the tenancy HTTP suite, which forwards a literal Host through a loopback Node reverse proxy. The test proves this application contract with that proxy. [Nginx example](../../infra/nginx/README.md)

## Deployment acceptance

Terminate public TLS at the reviewed edge. Nginx should send HTTP/1.1 with the validated original authority as the single Host and clear incoming forwarding and tenant identity headers. The default virtual host must reject unrecognized traffic. Serve dashboard auth at the exact dashboard origin. Probes should send an allowed Host and use infrastructure-only access controls.

Before deploying, prove Cloudflare-to-origin access restrictions from allowed and untrusted networks, public and origin TLS, header overwrite behavior, and firewall or private-network isolation of the API. Decide the final trusted client-IP policy and recheck abuse budgets for shared peers. Exercise the real Nginx/Cloudflare path, including duplicate/malformed authority, sibling hosts and cache isolation. Local tests do not establish these deployment gates.
