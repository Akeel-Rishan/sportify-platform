## ARM64 support path and limits

Node publishes a Linux ARM64 binary for this runtime. Next publishes [@next/swc-linux-arm64-gnu 16.4.6](https://registry.npmjs.org/@next/swc-linux-arm64-gnu/16.4.6), whose metadata declares `os: linux` and `cpu: arm64`; Next selects native packages for the installation target. pnpm 10, TypeScript, React, Nest and the process tooling run under Node, with no application-specific native bindings introduced here. Optional image/compiler/watch dependencies must still install and execute correctly on the future target.

**Actual execution is Windows x64 only.** No Linux ARM64 installation, container build or OCI deployment was executed. Docker compatibility, libc/base image selection, pool/database drivers and cloud capability checks remain later work. This support path is evidence to test, not an ARM64 test result.

## TypeScript, modules and build order

- `@sportify/shared-config/typescript.json` owns strict checks and the ES2022 target as a self-contained tooling export. Each project consumes it through a `workspace:*` development dependency; root `tsconfig.base.json` extends this same baseline. This avoids relative paths escaping a symlinked package during type-aware linting.
- Web uses Next's plugin, `module: esnext`, `moduleResolution: bundler`, DOM libs, isolated modules and noEmit. `next typegen` creates route types before typechecking a fresh checkout. No Next compilation output is used by API/worker.
- API compiles with `tsc`, Node16 resolution/CommonJS package mode, experimentalDecorators and emitDecoratorMetadata. Development combines compiler watch and Node watch after an initial build. This preserves decorator metadata when future dependency injection is introduced; production uses `node dist/main.js`.
- Worker uses Node16 resolution/CommonJS and Node types. `tsx watch` is development-only; production uses `node dist/main.js`. Its timer is explicitly idle, with only shutdown signal listeners and no job work or connections.
- `shared-types` builds an empty entry; `api-contracts` builds framework-independent transport/error/health contracts. `validation` builds a framework-independent environment parser using Zod; it never reads process environment or files. These packages have explicit `types`, `require` and default exports. No domain abstraction is invented. `shared-config` exposes only a JSON tooling subpath; importing its root into a browser is not supported.
- No shared package imports an application; no API/worker dependency points to web. No app imports server runtime configuration into browser code. Future runtime package consumers must declare actual `workspace:*` dependencies so pnpm can order their builds; do not add unused dependencies or editor-only aliases.
- `pnpm -r build` is topological: shared-config and validation precede their consumers. Typecheck, lint and tests first build shared outputs; root dev does likewise. Independent API/worker dev scripts also build their workspace dependencies, so fresh checkouts do not require stale output.
- Native build-script permissions are explicit for esbuild and sharp. Nest's optional donation-message postinstall is not needed for runtime. A frozen-lockfile install checks graph consistency; future dependency additions must review their script requirements.

## Step 04 API transport compatibility

The installed Nest 11.2.10 Express adapter uses Express 5.2.1. Framework/runtime versions remain unchanged. Only `@types/express` 5.0.6 was added as a development dependency ([official registry metadata](https://registry.npmjs.org/@types/express/5.0.6)); its Express core declaration major is 5. API now consumes api-contracts through `workspace:*`. Existing Zod validates DTO schemas as well as configuration; no competing validator or logging framework was added.

Production preserves Node16/CommonJS compilation and emitted legacy decorator metadata. API typechecking includes `test/`; production build overrides rootDir back to `src` and excludes tests. A scoped Vitest/Vite plugin uses existing TypeScript 5.9.3 `transpileModule` with matching decorator metadata flags for API source/tests only. Other projects retain their existing transform. DTO validation is exercised through real HTTP to verify metadata survives this path; these tests do not change production module settings.

Installed core source was inspected: `nest-application.js` registers parsers during init before module middleware; `routes-resolver.js` attaches its global exception layer after routing and maps malformed JSON into a framework 400; the Express adapter retains default bounded parsers. Configure early `app.use()` before init, then use the same configuration in production and HTTP fixtures. Real malformed/oversized HTTP tests validate the ordering instead of relying only on documentation. See [API conventions](../api/conventions.md).
