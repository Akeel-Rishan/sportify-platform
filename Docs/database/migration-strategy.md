## Provisioning sequence and privileges

1. Approve design blockers and record the exact target ATP release/compatibility, AL32UTF8 charset, character/byte limits, timezone-file support and secure connection mode. Provision ATP first; an account cannot be created in a database that has not been provisioned. Source SCHEMA section 9 reverses these two steps and is superseded by this explicit order.
2. Use a separately controlled administrator to create SPORTIFY_SCHEMA_OWNER and restricted runtime accounts. Schema owner owns all application tables and migration DDL. Runtime account names identify connecting principals, not separate tenant data schemas; all business objects remain in the one owner schema. Optional dedicated worker runtime may have a narrower grant set.
3. Grant owner only required create/alter privileges and tablespace quota in that database. Verify ATP permits the selected migration session-lock mechanism. Keep administrator/owner credentials outside application containers/environment and Git.
4. Prefer initially locked/no-runtime access while installing/verifying. After verification, give runtime CREATE SESSION and explicit object SELECT/INSERT/UPDATE/DELETE only where needed; schema-qualify object names or use reviewed private synonyms. No ANY privileges, owner role, administrative role, CREATE TABLE, registry writes or migration DBMS_LOCK privilege for runtime. Identity-backed inserts must be tested under direct grants; do not guess broad sequence grants or permit identity override from public APIs.
5. For immutable booking/payment/audit history, omit DELETE; audit gets INSERT/approved restricted reads, no UPDATE. Grant slot DELETE for authorized transactional release and guarded state/queue UPDATE where needed. Consider column-level UPDATE privileges or reviewed packages for immutable-field protection; source row CHECKs do not enforce immutability. Same-account direct DML is not tenant row authorization: all repositories require tenant context. Separate restricted reporting views/READONLY and maintenance roles are later, explicitly reviewed grants.
6. Set UTC on every migration and application connection; later pools initialize each new session and verify/reset checkout state. Configure verified TLS/ACL/secrets separately for local/staging/pilot/production. Never use ADMIN for API requests, share wallets in Git, or use production as normal development.

## Single runner across DDL commits

A registry row lock alone is insufficient because Oracle DDL commits release transaction locks. Require a schema-specific exclusive session advisory lock, such as a reviewed DBMS_LOCK wrapper with `release_on_commit => FALSE`, held by the same session that executes all migration DDL. Allocate a name/handle before business DDL; ALLOCATE_UNIQUE itself can commit and must not be called in an unrelated business transaction. Bounded acquisition failure exits without applying. Verify return codes, session ownership, release and disconnect behavior on the actual ATP release. Runtime accounts receive no privilege to request these locks.

If the ATP privilege/service cannot support that mechanism, stop and approve an equivalent externally fenced single-runner design before execution; never silently fall back to row locking. CI concurrency is additional protection, not proof against a second operator/session. An orchestrator must not hold a lock in one connection while executing DDL in an unprotected different connection, and loss of the executing connection invalidates its run.

## SQL execution and verification

Recommend a small future TypeScript orchestration command compatible with the existing workspace, using a pinned SQLcl script-mode executor in the same protected database session, or an explicitly structured node-oracledb statement manifest. No migration package/driver/client is installed in Step 05. SQLcl availability/platform and target connection/grant support must be verified before selecting that implementation.

SQLcl scripts use explicit stop-on-error behavior (`WHENEVER SQLERROR EXIT SQL.SQLCODE ROLLBACK` and OS-error handling) and controlled SET DEFINE OFF where appropriate. Those are client commands, not database SQL. A driver manifest executes ordinary SQL without a trailing semicolon/slash, while PL/SQL blocks retain internal semicolons and are submitted as complete blocks. Slash lines delimit client blocks and are not sent as standalone SQL. Never split arbitrary SQL/PLSQL text on every semicolon, interpolate credentials into shell arguments, print wallets or swallow object-exists errors.

After each migration verify named tables/columns/types/defaults, exact PK/UK/FK/check definitions, enabled/validated constraints, valid objects/indexes, reviewed seed rows and ledger checksum/state. ## Partial failure, recovery and destructive safeguards

Oracle implicitly commits before syntactically valid DDL (even if the DDL errors) and after successful DDL. A multi-statement migration is not rollback-atomic. ROLLBACK only affects still-uncommitted DML; successful earlier DDL remains. Never mark APPLIED solely because the process exited or because tables exist.

On failure: stop the run/deployment; retain FAILED/RUNNING evidence and exact immutable artifact checksum; inspect secured per-step logs and Oracle catalogs. Do not blindly rerun bootstrap, ignore object-exists, delete ledger history, or start the application on an incomplete schema.

- Disposable dedicated development database/schema: after explicit destructive authorization and verification of environment/target, recreate a clean isolated schema and replay accepted immutable migrations. No automatic drop/recreate command is provided here.
- Unapplied remainder with an unambiguous manifest: an operator may authorize a same-checksum resume that verifies every already-applied step's exact postcondition and executes only the pending steps. Divergent definitions fail; presence alone is not success.
- Failed artifact requiring a fix or existing non-disposable data: apply a separately reviewed new repair migration through an explicit operator recovery path under the same session lock, verify the intended resulting schema, and link the original retained FAILED row's REPAIR_VERSION to that APPLIED repair. Normal runner only accepts such a reviewed repair if the repair row is APPLIED, checksums/postconditions match, and no link cycle/chain exists. Do not relabel the failed original as successfully executed. Alternatively restore a verified recovery point and replay. Restore safety/RPO/RTO remains Q-13.

Forward fixes are preferred for deployed schemas. Destructive changes need explicit owner approval, affected-row counts, retention/privacy review, verified backup/recovery and compatibility plan. Expand nullable/new structures first, migrate/backfill with validation, switch application reads/writes, then contract only after old versions are retired. Runtime privileges, FK validation and checksums are part of each release. Do not promise arbitrary rollback SQL can reconstruct lost financial/history data.
