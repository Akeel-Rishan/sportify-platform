# Pool, session and transaction ownership

Each application creates one process-local Oracle pool. API default maximum **8**, worker **2**. Minimum **0** avoids startup connection storms and lets liveness start while Oracle is unavailable; pool creation is not a connection claim. Increment **1**, idle shrink **60 seconds**. Validation caps maxima at 8/2 pending an explicit capacity review; minimum must not exceed maximum, and increment is positive and no larger than maximum.

Default queue wait **1500ms**, queue lengths **16 API / 4 worker**; connection establishment **5s**, transport **3s**, no retries, ping after **60s idle** with **1500ms** ping timeout. Borrowed connection `callTimeout` defaults to **1500ms** per round-trip. Configurable queue/call bounds are 100–5000ms; idle 10–3600s. These are driver operation budgets, not a single overall HTTP SLA: acquisition, checkout reset, query, rollback and release are successive operations, and a database call may use multiple round-trips. Target/network failure latency must be measured; never treat a Promise.race timeout that abandons a later connection as safe cancellation. Readiness coalesces simultaneous probes and caches both outcomes for 1s after completion.

Local live follow-up, 22 November 2026: a 1500 ms acquisition failed with NJS-040 during cold connection establishment. The two ignored application environment files now explicitly set `ORACLE_QUEUE_TIMEOUT_MS=5000` within existing bounds; the successful live verification used the same override. This is a measured local setting, not a global default change or a proven capacity/SLA guarantee. No unbounded wait, TLS weakening or write retry was added. See [live evidence and limitations](oracle-verification.md).

Replicas multiply connections: `8 × API replicas + 2 × worker replicas`, plus migration/operator/monitoring sessions and target service limits. These are initial limits, not a Free-tier capacity guarantee. Pool aliases/global singleton registries are not used. The application factory owns the pool, accepts a test-only injected factory, cleans it after Nest construction/listen failure, and closes it during lifecycle shutdown. Worker owns no HTTP listener or job execution. It remains idle after pool initialization and makes no claim it connected successfully.

## Scoped work

`withConnection(callback)` and `query(sql, namedBinds)` acquire a session, set callTimeout, roll back inherited unfinished work, then execute fixed `ALTER SESSION SET TIME_ZONE = 'UTC'` **on every checkout**, including reused sessions. Scoped facades expose only parameterized execute, never the raw connection/commit/close. Await calls sequentially and return materialized values; do not start detached work, use DDL, change transaction control, return LOBs/streams or retain a facade. A retained facade rejects new execution after callback completion. Values are named binds (strings, safe integer numbers or null); SQL is authored server code, never client-supplied SQL.

Ordinary scopes always roll back unfinished work in finally and release. `transaction(callback)` disables autocommit, commits once after success, rolls back on failure, and releases on every path. A rollback failure drops the session rather than returning uncertain state to the pool. Cleanup failures emit fixed classifications only. Original callback/commit failures retain their identity if rollback/release also fails; cleanup failure after successful work is reported as unavailable. No write/commit retry is performed: lost acknowledgement of COMMIT can mean the outcome is unknown, requiring future business idempotency.

Implicit nested pool scopes/transactions are rejected using per-pool AsyncLocalStorage. It tracks ownership only, not request identity or secrets, and concurrent independent scopes remain isolated in unit coverage. Shutdown disables this ownership store after the pool finishes closing. Reuse the callback's facade for additional operations in one transaction. There are no inner commits/savepoint semantics or generic repositories.

## Exact values and UTC

Every NUMBER is fetched as a string using an execute-local driver fetchTypeHandler **before** JavaScript numeric conversion, not by stringifying a potentially rounded number. Keep internal NUMBER IDs and NUMBER(12,2) money as decimal strings; external UUIDs remain strings. Only explicitly bounded safe counts may be converted intentionally. Decimal money must never be bound as a floating-point number; bind its decimal string and use reviewed explicit SQL numeric conversion/format where needed. There are no global driver type overrides.

TIMESTAMP(6) has no timezone. The application contract is UTC wall-clock encoding with six fractional digits. Session UTC protects LOCALTIMESTAMP and session operations but does **not** fix driver Date conversion: driver 6+ binds/fetches plain DATE/TIMESTAMP in the application's timezone, and JavaScript Date retains only milliseconds. This helper disallows Date binds and rejects unprojected temporal columns. Use canonical strings, for example `2026-01-02T03:04:05.123456Z`, bind through `TO_TIMESTAMP(:instant, 'YYYY-MM-DD"T"HH24:MI:SS.FF6"Z"')`, fetch through `TO_CHAR(column, 'YYYY-MM-DD"T"HH24:MI:SS.FF6"Z"')` only for contractually UTC plain TIMESTAMP values. The Z is a literal marker, not conversion; timezone-bearing values require an explicit UTC conversion first. Validate real dates at the future DTO boundary. Do not route precise values through Date or assume every Oracle temporal type already contains UTC.

## Startup, outage, shutdown

Missing/invalid credentials, mTLS wallet settings or pool settings fail before resources are allocated. Wallet metadata/readability preflight runs before pool allocation; pool creation still does not assert successful wallet decryption or an mTLS handshake. Pool creation failure is safely classified and not retried. Default minimum zero performs no initial connection check; first readiness acquires/checks Oracle and returns 503 on failure. An outage after startup invalidates readiness on the next expired probe; recovery can restore it. Liveness is independent. Full business/schema readiness is outside this step.

During API shutdown the readiness lifecycle becomes unavailable and rejects new database scopes, HTTP closes, then the pool drains for **5 seconds** before driver-forced closure. Worker clears its idle timer/removes signal listeners/stops pool acceptance and closes once, even on repeated shutdown calls. Windows hard termination can bypass hooks; POSIX signal delivery and load-balancer draining remain deployment verification work. This is bounded driver drain, not a complete load-balancer draining implementation.
