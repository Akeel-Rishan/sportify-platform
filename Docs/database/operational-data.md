# Operational records and ownership

Status: **proposed Q-09/Q-11/Q-19/Q-23 design**. Exact columns/checks/indexes are in the linked dictionary/register. Worker/application code remains unchanged and idle. This document distinguishes transaction intent from execution and delivery evidence.

| Table             | Responsibility and transitions                                                                                                 | Claim/dedupe rule                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OUTBOX_EVENTS     | Versioned immutable event in the same transaction as domain changes; PENDING -> PROCESSED, or retry PENDING -> terminal FAILED | Dispatcher locks eligible rows with SKIP LOCKED, inserts deduplicated jobs and marks PROCESSED in one short transaction; no external I/O and no persistent claim lease needed |
| JOB_QUEUE         | Scheduled/retryable execution; PENDING -> RUNNING -> COMPLETED, retry back to PENDING or terminal FAILED/CANCELLED             | Commit bounded claim before work; LEASE_TOKEN, LEASE_EXPIRES_AT_UTC, LOCKED_BY/AT; conditional fenced acknowledgements and stale-lease reclaim                                |
| NOTIFICATIONS     | Email intent/recipient and outcome: QUEUED -> SENT/FAILED/CANCELLED                                                            | Scope + DEDUPE_KEY unique; one notification per logical action/recipient/language                                                                                             |
| NOTIFICATION_LOGS | Append delivery attempt/outcome evidence SENT/DELIVERED/FAILED/BOUNCED/UNKNOWN                                                 | Scope + notification + attempt unique; no replacement of earlier evidence                                                                                                     |
| IDEMPOTENCY_KEYS  | Owner-scoped request fingerprint and replay payload; PROCESSING -> COMPLETED/FAILED                                            | Unique tenant/operation/owner/key, bounded claim lease and conditional completion; re-authorize replay                                                                        |
| AUDIT_LOGS        | Append attributable business/security changes in the domain transaction                                                        | No ordinary update/delete API or runtime privilege; server actor/scope, safe field deltas and request ID                                                                      |

Outbox PROCESSING is a source-compatible dormant state: this design does not commit it before enqueue. A dispatcher crash before commit rolls back both enqueue and event marking; retry sees PENDING. Dedupe job keys derive from immutable outbox ID + handler/version. Parent business writes never wait on a dispatcher-held tenant lock; outbox dispatch does not acquire domain locks. Exactly-once execution is not promised.

Worker claims use a bounded cursor/batch over eligible status/due rows with `FOR UPDATE SKIP LOCKED`. Do not combine 19c row-limiting syntax with FOR UPDATE without testing supported SQL; use an explicitly tested ordered cursor/fetch strategy. The claim increments attempt_count, assigns a fresh fencing UUID, expiry and worker ID, then commits. Heartbeats extend only a matching live lease. Reclaim compares database time and creates a new fencing token. Every acknowledge/retry checks the token; a stale worker cannot commit queue state. Business handlers also use domain idempotency/unique natural keys so an expired lease cannot duplicate committed effects. External email calls happen outside DB locks; provider idempotency where available reduces, but cannot eliminate, crash-after-send duplicate risk.

JOB_QUEUE source max_attempts=5 is retained as a proposed initial retry bound; outbox also gains max_attempts=5. Backoff is exponential with bounded jitter/cap under reviewed configuration. No timing/retention values are falsely approved. Attempt ceiling leads to FAILED and operator inspection; cancel clears lease fields. Raw provider exceptions/stacks never enter LAST_ERROR/RESPONSE_SUMMARY; use an allowlisted code. Operators requeue only with audited reason and duplicate-safe handling. Global/tenant scope is explicit; a NULL tenant is never a wildcard for a tenant-owned operation.

## Account email before a tenant exists

Source NOTIFICATIONS requires TENANT_ID, so it cannot represent pre-tenant verification/reset email. Proposed notifications/logs permit platform rows and add non-null SCOPE_TENANT_ID: 0 for platform, exact positive tenant ID otherwise. Parent scope key plus scope FK prevents a platform log from referencing tenant notification data; the tenant FK remains for tenant rows. Platform notifications require a global recipient user and no booking relationship. Templates are global-only and EMAIL-only for MVP; tenant-custom templates, SMS, WhatsApp and in-app channels remain dormant. Do not infer that a customer gains a global account merely because a notification contains an email address.

## Hash-only tokens and safe replay

Q-09 is a security design gate: a digest cannot reconstruct a token for asynchronous email or replay. Proposed mechanism for one-time email/reset/invitation/hold tokens: derive a high-entropy HMAC-SHA-256 token using an external, purpose-separated versioned key and canonical immutable context (random PUBLIC_ID, action purpose, relevant user/tenant/checkout binding and UTC expiry). Store only SHA-256(token), record public ID, and TOKEN_KEY_VERSION. Workers hold an explicitly authorized external key access path and reconstruct the token transiently; outbox/job payloads carry only record references/version. Validate digest, purpose, expiry, consumption/revocation and caller ownership before use; changing context invalidates prior derivations. No key material or raw token is stored in Oracle payload/body/audit columns. Session tokens remain random client cookies with stored digest only.

NOTIFICATIONS.MESSAGE_BODY is nullable intentionally: action emails are rendered transiently, never persist a raw action URL/token there. Templates contain placeholders only. Reconstructed action URLs must be omitted from provider/log summaries. Secure email providers necessarily receive the recipient/action message; provider logging/retention is a separate reviewed policy. Key rotation retains bounded access to versions needed by unexpired actions, then retires them. This is a recommendation requiring a security review and cryptographic test vectors; no homegrown crypto implementation is added now. An alternative encrypted secret broker requires explicit approval because the source hash-only-storage rule must not be silently weakened.

IDEMPOTENCY_KEYS binds OWNER_SCOPE to SHA-256 of a versioned canonical encoding of server-proven stable user identity or high-entropy checkout-proof digest, tenant and operation, never an arbitrary submitted owner ID. This stable digest is not a credential and does not change on session/key rotation; authorization is independently rechecked. Keys/fingerprints include tenant, operation/resource and semantic validated payload. Different fingerprint with same key conflicts. Completed replay rechecks ownership/authorization and emits a fresh Step 04 request ID; cache the stable application payload/status, not the old transport envelope. Raw hold/action tokens never enter RESPONSE_BODY; reconstruct only for the same proved checkout using the reviewed token mechanism. Existing source promises of original body replay must be amended for per-request transport IDs. PII-bearing replay payloads are bounded/restricted and purge only after an approved retry/privacy window. Reclaim of PROCESSING uses fencing and domain result lookup, not blind re-execution after ambiguous commits.

## Audit, retention and flexible data

Actor types: USER (global user and, for tenant work, matching tenant membership), PLATFORM_ADMIN (matching global admin/user pair; tenant may describe the target, not actor authority), WORKER/SYSTEM (allowlisted service, no invented account), or GUEST (pseudonymous proved checkout key, no fabricated user). All-or-none actor checks supplement foreign keys. Sensitive before/after data is a redacted field allowlist, never a full object dump; immutable audit PUBLIC_ID supports browser lookup without internal numeric IDs.

Generic payload fields are justified only for versioned event/job messages, bounded replay results, redacted audit deltas, message/template prose, policy prose or non-sensitive wizard UI state. Core booking, pricing, ownership, limits and financial facts remain relational. PLATFORM_SETTINGS is a controlled non-secret registry; it does not hold deployment credentials or bypass relational constraints. ONBOARDING_PROGRESS.STEP_DATA cannot become a second business profile or store passwords/tokens. No retention period is invented: Q-23 must approve numeric windows, legal/financial retention and access/purge owners before a purge job is enabled. Financial/audit/history parents are retained; token/session eligibility checks expiry even before any eventual purge.
