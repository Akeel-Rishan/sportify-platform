### VPD and application context

ARCH §8.2 requires evaluation of VPD as additional protection. The deployed schema has zero policies visible in `USER_POLICIES`, and the manifest has no application-context creation or VPD policy. The pool resets transaction state and timezone. It has no mechanism to bind and clear a tenant context. Oracle application contexts can carry trusted session identity and VPD can use it to filter rows. Pooled sessions retain state, so an implementation would require setting fail-closed context for each checkout, clearing it on every release and discarding connections on reset failure. Shared worker and platform jobs need separately authorized scope handling. [Oracle VPD](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbseg/using-oracle-vpd-to-control-data-access.html) · [Oracle application contexts](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbseg/application-contexts.html) · [node-oracledb 26 session state](https://node-oracledb.readthedocs.io/en/v26.0.0/user_guide/connection_handling.html)

**Review decision:** keep D-02 tenant predicates, backend authorization and composite keys mandatory. Defer VPD/context deployment for the MVP foundation. This optional defense may be reconsidered after tenant repositories and per-operation grants are modeled. Before enabling it, verify availability and privileges on the target, fail-closed missing context, isolation across pooled borrowers and privileged versus public paths on live Oracle. The current review records the evaluation. It grants no context or policy privileges and changes no approved decision.
