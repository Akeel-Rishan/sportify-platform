# Step 09 approved audit and operational storage rules

**Structural policy approved under D-24; storage and test-only Oracle protocols verified under D-27.** Numeric operating values, collection/retention and secret replay behavior remain undecided. [Operator gates](step09-verification.md). No audit emitter, dispatcher, worker processor, request-idempotency middleware or notification delivery is implemented.

## Scope and audit privacy

AUDIT_LOGS, OUTBOX_EVENTS, JOB_QUEUE and IDEMPOTENCY_KEYS require SCOPE_KIND. TENANT requires a real tenant FK; PLATFORM requires tenant NULL. NULL alone never selects platform authority. Future services derive scope and principal server-side and authorize each read/write.

Audit records carry UTC event time, action/target, public event ID, request ID and payload version. Tenant USER actors require matching membership/user/tenant references; platform administrators require matching admin/global-user references. WORKER/SYSTEM actors use a service classification without invented user identity; approved GUEST actors use a pseudonymous scope. Polymorphic entity references are descriptive, not pretend generic FKs. Restrictive actor FKs retain attribution; erasure/pseudonymization and exceptions need an explicit privacy policy before any purge service.

Before/after CLOBs must satisfy IS JSON STRICT WITH UNIQUE KEYS. They are optional, versioned, allowlisted **minimal changes**, never automatic full-record dumps. JSON validity does not establish business shape, size or privacy safety. Each later emitter must define a bounded payload schema and redact passwords, hashes, raw tokens, authorization/cookies, connection information, bodies and unnecessary customer/payment personal data. IP/user-agent collection and numeric retention periods remain deferred; nullable source fields are not permission to collect them.

Current runtimes have no audit object grants because no emitter exists. When a reviewed emitter is implemented, grant only its required INSERT and carefully scoped reads, never UPDATE/DELETE. A separate controlled retention identity/process would need explicit approval. The owner/DBA can change data: this is not tamper-proof storage. Test-owner checks verify current denials after positive runtime identity/connectivity, rather than treating connection failures as access-denial evidence.

## Outbox to jobs

OUTBOX_EVENTS is durable business-event intent inserted in the same transaction as its source change. The approved handoff design requires a future dispatcher to lock a due event, inserts one JOB_QUEUE row per intended consumer, and marks the event PROCESSED in one transaction. UQ_JOB_EVENT_CONSUMER prevents duplicate (source event, consumer) jobs while permitting fan-out. Two source FKs enforce both scope and tenant; a platform event cannot become a tenant job through a nullable-tenant bypass. Independent jobs have both source/consumer absent.

Outbox attempts represent handoff attempts only. Job attempts represent execution only; do not run two delivery retry loops for the same task. The unapproved five-attempt defaults are removed from SQL, dictionary and manifest. MAX_ATTEMPTS, outbox AVAILABLE_AT_UTC and job RUN_AFTER_UTC are required explicit insertion inputs; no retry cap or immediate scheduling policy is inferred. Attempt counts are bounded by the supplied positive MAX_ATTEMPTS. Backoff/lease/retention values must be explicit future operating configuration; none is invented here.

Future claiming uses a bounded transaction and row locks, sets RUNNING with nonblank owner, UUID lease token, lock time and finite expiry, and increments attempts. Expired leases may be reclaimed only below the attempt cap, with a fresh token. Completion/retry updates must include expected state, ownership/token and unexpired lease; stale workers affect zero rows. Terminal COMPLETED/FAILED timestamps and cleared lease fields are constrained. Terminal failure is retained for operator review, not silently retried forever. External work happens outside a database lock transaction and requires its own idempotency; exactly-once execution is not promised.

The test harness uses direct-key SELECT FOR UPDATE SKIP LOCKED on separate sessions, not FETCH FIRST combined with FOR UPDATE (unsupported in the consulted 19c syntax). Lease expiry is set through explicit synthetic historical times rather than sleeps. No production worker code or polling loop is added. Notification templates/records/deliveries remain assigned to a later step; no minimal notification table is needed for these migrations.

## Request idempotency

The full unique key is (SCOPE_KIND,TENANT_ID,OPERATION_SCOPE,OWNER_TYPE,OWNER_SCOPE,IDEMPOTENCY_KEY). Owner type is USER/GUEST with a server-proven hashed owner scope; it is not client authorization. Operation namespace and key are nonnull. Platform TENANT_ID is NULL but the remaining components are nonnull: Oracle rejects a repeated **partially null** composite tuple with identical nonnull components. Only an entirely null index key is omitted. This behavior requires actual Oracle tests for both platform and tenant keys before release. No fake tenant zero or nullable-only unique key is used.

The approved fingerprint design is SHA-256 over validated canonical application inputs, including the operation/version/owner context required by the later endpoint. The helper in tests canonicalizes synthetic plain JSON only; it is not production canonicalization or authorization. Future endpoints must define canonical decimal/date/array semantics and refuse ambiguous input. Same authorized scope/key with the same fingerprint replays only a completed, permitted result; a different fingerprint conflicts; a processing claim returns the approved bounded conflict behavior. A unique key alone implements neither replay nor authentication.

Processing records have a UUID lease, creation/record expiry and bounded lease expiry. Completion clears the lease and stores a safe versioned JSON result/reference and status; FAILED is separate from successful completion. Failed/unknown claims require explicit reconciliation, not a successful replay or a fabricated in-progress result. Result payloads exclude secrets/tokens and PII beyond the minimal authorized representation. Replay reconstructs a fresh request ID/envelope and rechecks authorization. Guest secrets need a separately approved secure reconstruction design; this schema is not approval to persist plaintext bearer secrets.

Business DML, result completion, audit and event intent must share the relevant transaction. A rollback cannot leave a successful replay marker. An uncertain commit requires reconciliation, never blindly repeating writes. Expired rows retain uniqueness until an authorized reconciliation/cleanup policy removes or supersedes them; expiry does not grant immediate key reuse. Numeric TTLs, lease lengths, retry budgets, backoff and retention/purge remain future explicit policy/configuration, with no cleanup job in this step. The isolated harness supplies synthetic retry budgets and historical/short lease timestamps only to test boundaries; those values never become runtime defaults or seeds. Migration/driver/harness wait budgets from earlier steps remain verification controls, not job-processing policy.
