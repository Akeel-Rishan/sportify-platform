# SPORTIFY – Complete Oracle Database Schema Specification & ERD

**Document version:** 1.0  
**Product:** SPORTIFY – Multi-Tenant Indoor Sports Booking & Business Management SaaS  
**Source baseline:** Master PRD v1.0, MVP Scope & Business Workflow Specification v1.0, Technical Architecture Specification v1.0  
**Database:** Oracle Autonomous Transaction Processing (ATP)  
**Architecture:** Shared database, shared schema, tenant-aware relational model  
**Target SQL compatibility:** Oracle Database 19c-compatible syntax; verify against the exact Autonomous Database release before production  
**Status:** Engineering baseline – requires staging execution and validation

---

## 1. Purpose and scope

This specification defines the logical relational model, table structures, data types, keys, constraints, indexes, tenant-isolation rules and booking-reservation design for SPORTIFY.

The bootstrap DDL is supplied separately in `001_sportify_schema.sql`. It creates **61 tables**, named constraints and indexes, and initial global reference data. The design includes:

- All 48 table groups listed in the Master PRD database-design section.
- Supporting tables required for authentication, sessions, invitations, idempotency, background jobs, transactional outbox, onboarding and subscription invoicing.
- `BOOKING_HOLD_ITEMS`, added to support the same multi-resource reservation model used by booking items.

The schema is a shared-schema multi-tenant design. A tenant is one registered sports business. The initial model enforces one business record per tenant, while a business can have multiple locations and each location can have multiple bookable resources. Day-of-week values in `OPERATING_HOURS` use ISO numbering (1=Monday through 7=Sunday); business-wide holidays are represented by a closure row for each affected location.

### MVP versus future-ready tables

The schema includes tables for both MVP and PRD roadmap capabilities. Their presence does not mean their user interface or API must ship in the MVP. The bootstrap creates 61 tables, includes all 48 PRD-listed tables, and adds 13 supporting tables.

**MVP-critical areas:** identity, tenant membership, roles and permissions, business profiles, locations, sports, resources, operating hours, holidays, availability blocks, pricing, customers, holds, bookings, booking items, slot reservations, cancellations, manual payments, subscription controls, website settings, media, notifications/outbox, audit and idempotency.

**Future-ready / dormant until later phases:** recurring booking series, payment gateway transactions and webhooks, custom domains and verification, marketplace listings, reviews and responses, and advanced support workflows.

## 2. Core design decisions

| Area | Decision |
|---|---|
| Tenant model | One tenant per registered sports business |
| Database topology | One shared Oracle ATP database and shared schema |
| Tenant ownership | `TENANT_ID` on every tenant-owned record |
| Cross-tenant relationships | Composite foreign keys including `TENANT_ID` |
| Internal keys | Oracle identity `NUMBER` keys |
| Public identifiers | Application-generated UUID strings in `VARCHAR2(36)` |
| Time storage | `TIMESTAMP(6)` without time zone, with UTC-only convention for `*_UTC` fields |
| Database session timezone | Set every pooled connection to UTC |
| Currency | `NUMBER(12,2)` plus ISO 4217 `CHAR(3)` code |
| Phone | E.164 text in `VARCHAR2(16)` |
| Bookable unit | 15-minute time segment in MVP |
| Double-booking guard | Primary key on tenant, resource and slot start |
| Deletion | No cascading deletes for financial, booking, tenant or audit records |
| Files | OCI Object Storage; database stores object keys and metadata |
| Application access | Restricted runtime database account; no ADMIN account for normal requests |

### Why internal numeric IDs and public UUIDs?

Numeric identity keys provide compact joins and indexes. Public UUIDs are used in URLs and external API responses so that sequential database identifiers are not exposed as public references. The application must generate UUIDs before inserting rows; public IDs are not automatically generated by this DDL.

### Why plain `TIMESTAMP(6)` for UTC columns?

Oracle does not permit `TIMESTAMP WITH TIME ZONE` columns in primary-key or unique-key definitions. `RESOURCE_SLOT_RESERVATIONS.SLOT_START_UTC` must be part of a unique primary key. Therefore all `*_UTC` fields use `TIMESTAMP(6)` without a time-zone component and follow a strict UTC convention. The application converts local venue times using the tenant/location IANA timezone before binding values.

The DDL uses `DEFAULT LOCALTIMESTAMP` for creation/update timestamps. Consequently, **every database pool session must execute `ALTER SESSION SET TIME_ZONE = 'UTC'`** when it is created. Never depend on the VM or database server's local timezone.

## 3. Entity relationship overview

The ERD is split into three diagrams to remain readable:

1. `SPORTIFY_ERD_01_Core.mmd` – tenants, users, roles, businesses, branches, sports and resources.
2. `SPORTIFY_ERD_02_Booking_Payments.mmd` – customers, holds, bookings, slot reservations, payments and subscriptions.
3. `SPORTIFY_ERD_03_Platform_Website.mmd` – authentication, platform administration, websites, domains, notifications, support and marketplace.

These are Mermaid ER diagrams and can be opened in Mermaid-compatible Markdown editors or Mermaid Live Editor.

### Core relationship rules

- One tenant has zero or one business during onboarding; a completed tenant has one business.
- One business has one profile, many locations and many enabled sports.
- One location has many resources.
- A resource's sport must be enabled for its business through `BUSINESS_SPORTS`.
- One customer can have many bookings within the same tenant.
- A booking has one or more booking items. The MVP application must create exactly one item per booking; the schema permits multiple items for future multi-resource bookings. `CUSTOMERS.USER_ID` is optional so a future registered customer account can be linked to that tenant’s customer record.
- A booking hold has one or more hold items.
- Each active resource-time segment has exactly one row in `RESOURCE_SLOT_RESERVATIONS`.
- A slot row belongs to exactly one booking item or one hold item, never both.
- A booking can have multiple payment receipts and multiple refund records.
- Platform subscription invoices and payments are separate from customer venue-booking payments.

## 5. Tenant isolation and composite-key strategy

### 5.1 Mandatory rule

Every tenant-owned table includes `TENANT_ID`. The tenant identifier is derived by the backend from the authenticated user's membership or from a validated website hostname. It must never be trusted merely because a browser sends a `tenant_id` field.

### 5.2 Composite parent keys

Tenant-owned parent tables expose composite unique keys such as:

- `BUSINESSES (TENANT_ID, BUSINESS_ID)`
- `LOCATIONS (TENANT_ID, LOCATION_ID)`
- `RESOURCES (TENANT_ID, RESOURCE_ID)`
- `CUSTOMERS (TENANT_ID, CUSTOMER_ID)`
- `BOOKINGS (TENANT_ID, BOOKING_ID)`
- `BOOKING_ITEMS (TENANT_ID, BOOKING_ITEM_ID)`
- `BOOKING_HOLDS (TENANT_ID, HOLD_ID)`

Child tables reference these composite keys. For example, a booking item references `(TENANT_ID, BOOKING_ID, BUSINESS_ID)` and `(TENANT_ID, BUSINESS_ID, LOCATION_ID, RESOURCE_ID)`. This prevents an item from joining a booking in one tenant to a resource in another tenant or another business.

### 5.3 Application enforcement

Every repository method for tenant-owned data must require an authenticated tenant context. Query patterns must include `TENANT_ID` even when the primary key is globally unique.

Do not expose unrestricted repository methods such as `findById(id)` for tenant-owned entities. Use tenant-scoped methods such as `findByTenantAndId(tenantId, id)`.

### 5.4 Oracle VPD

Oracle Virtual Private Database (VPD) and application contexts may be added as defense in depth after the pooled-session context lifecycle has been tested. They are not a substitute for the composite foreign keys and backend authorization in this schema. If VPD is introduced, set context on every connection checkout and clear it before returning the connection to the pool.

## 6. Booking slot uniqueness and transaction model

### 6.1 Reservation table

`RESOURCE_SLOT_RESERVATIONS` is the final concurrency guard. Its primary key is:

```sql
PRIMARY KEY (TENANT_ID, RESOURCE_ID, SLOT_START_UTC)
```

`SLOT_START_UTC` is a plain `TIMESTAMP(6)` containing UTC. Each row represents one 15-minute slot. The row must point to exactly one of `BOOKING_ITEM_ID` or `HOLD_ITEM_ID`. Composite foreign keys also ensure that the slot row’s `RESOURCE_ID` matches the resource on its owning booking item or hold item.

This design means two transactions cannot commit the same resource-time unit. Oracle enforces the primary key even if two customers submit requests at almost exactly the same time.

### 6.2 Example

A booking from 19:00 to 20:00 reserves four rows:

| Tenant | Resource | Slot start UTC |
|---|---|---|
| 10 | 501 | 19:00 |
| 10 | 501 | 19:15 |
| 10 | 501 | 19:30 |
| 10 | 501 | 19:45 |

The application must convert local venue time to UTC before generating these slot starts.

### 6.3 Hold creation transaction

1. Resolve tenant and validate public booking configuration.
2. Begin Oracle transaction.
3. Lock the resource row using `SELECT ... FOR UPDATE` (for a multi-resource future booking, lock resources in ascending ID order).
4. Expire stale holds relevant to the requested resource/time range and delete their slot rows in the same transaction.
5. Validate operating hours, holiday, availability blocks, resource status and pricing.
6. Create `BOOKING_HOLDS` and `BOOKING_HOLD_ITEMS`.
7. Insert one `RESOURCE_SLOT_RESERVATIONS` row per 15-minute slot.
8. Insert idempotency and outbox data as required.
9. Commit.
10. If the primary key is violated, roll back and return HTTP 409 `SLOT_UNAVAILABLE`.

### 6.4 Booking confirmation transaction

1. Lock the hold row with `SELECT ... FOR UPDATE`.
2. Verify tenant, hold token hash, active status and expiry using database time.
3. Create `BOOKINGS` with `BOOKING_STATUS='CONFIRMED'` and `PAYMENT_STATUS='UNPAID'`.
4. Create the corresponding `BOOKING_ITEMS` rows.
5. Update slot reservation rows from `HOLD_ITEM_ID` to `BOOKING_ITEM_ID`.
6. Mark the hold `CONVERTED`.
7. Write audit and notification/outbox records.
8. Commit.

The conversion must be atomic. Never release the hold and then attempt a separate booking insert.

### 6.5 Expiry and cancellation

- When a hold expires, mark it `EXPIRED` and delete its slot reservation rows in the same transaction. Keep the hold and hold-item history.
- When a booking is cancelled, mark the booking and item cancelled, write a cancellation record, and delete the corresponding active slot rows in the same transaction.
- Completed and no-show bookings retain their historical booking rows. Historical slots may remain for audit; no new booking should be accepted for a past time.
- A delayed worker must not keep expired holds blocking availability. Every new hold transaction must re-check and clean expired holds for the requested slots.

### 6.6 Additional application invariants

The DDL cannot enforce every cross-row business calculation. The service layer must also enforce:

- The requested start time and end time align to the 15-minute grid.
- `DURATION_MINUTES` equals `END - START` and is a multiple of 15.
- A booking's header total equals the sum of its item totals.
- The MVP creates exactly one booking item per booking.
- Pricing rules for a resource do not overlap in their effective period.
- A maintenance block cannot silently overlap an existing confirmed booking.
- Payment receipts do not exceed the outstanding amount unless an explicit overpayment policy is introduced.
- Refund totals do not exceed the net received amount.

## 7. Status and financial rules

### Booking status

`BOOKINGS.BOOKING_STATUS`:

- `CONFIRMED`
- `CANCELLED`
- `COMPLETED`
- `NO_SHOW`

### Payment summary status

`BOOKINGS.PAYMENT_STATUS` is stored separately:

- `UNPAID`
- `PARTIALLY_PAID`
- `PAID`
- `PARTIALLY_REFUNDED`
- `REFUNDED`

The payment service updates this summary in the same transaction as receipt/refund changes. The individual receipt rows in `PAYMENTS` have `RECEIVED` or `VOIDED` status. Refund history is stored separately in `REFUNDS`.

### Venue payment versus SPORTIFY subscription payment

These are different money flows and must never be mixed:

- `PAYMENTS` / `PAYMENT_TRANSACTIONS` / `REFUNDS`: customers paying a sports venue.
- `SUBSCRIPTION_INVOICES` / `SUBSCRIPTION_PAYMENTS`: a sports business paying SPORTIFY.

### Monetary values

Use `NUMBER(12,2)` for Sri Lankan rupee amounts and a three-character currency code. Never use `FLOAT`, `BINARY_FLOAT` or `BINARY_DOUBLE` for financial amounts. Store the hourly rate and total as snapshots on booking items so later price changes do not rewrite historical bookings.

## 8. Indexing strategy

The DDL creates primary-key and unique indexes through constraints plus explicit indexes for common queries and foreign-key maintenance. Static inspection found 61 table definitions, 361 named constraints and 90 explicit indexes; all 48 PRD table names are represented. These are source-level checks, not an Oracle compilation result.

Critical access paths include:

- Tenant status and tenant membership lookup.
- Business locations and resource lookup.
- Resource availability by tenant, resource and time range.
- Active availability blocks by resource/location and time.
- Booking search by tenant, status, customer, business and creation date.
- Booking items by resource and start time.
- Slot reservations by their composite primary key, booking item and hold item.
- Customer search by tenant and mobile number.
- Payments by booking and receipt time.
- Subscription status and expiry.
- Website subdomain and domain hostname resolution.
- Notification, outbox and job queues.
- Audit history by tenant, actor and timestamp.

Do not add indexes without checking query plans and write overhead. Every new foreign key should be reviewed for a supporting index. Oracle's database development guidance recommends indexing foreign keys where appropriate, particularly when parent rows may be updated or deleted.

### 9.2 Tenant provisioning transaction

When a new tenant is created, the application must, in one transaction:

1. Insert `TENANTS`.
2. Insert `BUSINESSES` when the business profile is created.
3. Insert the owner `TENANT_USERS` membership as `ACTIVE`.
4. Create tenant roles `BUSINESS_OWNER`, `BUSINESS_MANAGER` and `RECEPTIONIST` in `ROLES`.
5. Map the approved permission catalog into `ROLE_PERMISSIONS`.
6. Assign the owner role in `USER_ROLES`.
7. Create onboarding progress rows.
8. Create `WEBSITE_SETTINGS` with the selected default theme and unique subdomain slug when the business is ready.
9. Create the initial trial subscription according to the configured trial policy.

The application must not rely on frontend-only role seeding. Staff invitations and support-ticket openers must reference a membership in the same tenant; the DDL uses tenant-aware membership foreign keys for these relationships.

## 10. Database users and grants

Do not run the application as Oracle `ADMIN`.

Create separate database accounts:

| Account | Responsibility |
|---|---|
| Schema owner | Owns DDL, migrations and schema objects |
| Runtime application user | Executes required application DML and approved sequences/packages |
| Read-only reporting user | Read-only access to approved reporting views |
| Maintenance operator | Controlled maintenance and export tasks |

The runtime account must not have `CREATE ANY TABLE`, unrestricted DDL or administrative privileges. Grant only the required object privileges. If stored procedures/packages are added later, grant `EXECUTE` only on those packages.

The exact grants depend on whether the deployment uses one schema with direct grants or a separate runtime schema with synonyms/views. That account layout must be finalized before provisioning the production database.

## 11. Migration and execution procedure

`001_sportify_schema.sql` is a **first-time bootstrap script**, not an idempotent full migration. It should be run once against a newly created, dedicated application schema.

Recommended process:

1. Provision a non-ADMIN schema owner.
2. Confirm the target Autonomous Database version and compatibility settings.
3. Set the connection session timezone to UTC.
4. Execute the bootstrap in SQLcl or SQL Developer using script mode.
5. Review the complete execution output; stop on the first DDL error.
6. Verify object counts and invalid objects in `USER_OBJECTS`.
7. Verify constraints in `USER_CONSTRAINTS` and indexes in `USER_INDEXES`.
8. Run seed-data checks.
9. Run application integration tests against a staging database.
10. Only after successful tests, create runtime grants and deploy the API.

The `SET DEFINE OFF` command is a SQL*Plus/SQLcl script setting. If the DDL is executed through a driver that sends statements individually, omit that command and execute each SQL statement separately.

### Required UTC session initialization

Example Node.js pool configuration concept:

```ts
sessionCallback: async (connection) => {
  await connection.execute("ALTER SESSION SET TIME_ZONE = 'UTC'");
}
```

Ensure this callback runs for every newly created pooled session. The application must also bind all `*_UTC` values as UTC values.

### Migration discipline

- Never edit an already-applied migration in place.
- Add a new migration for every schema change.
- Record version, checksum and installation time in `SCHEMA_MIGRATIONS`.
- Prefer backward-compatible expand-and-contract migrations.
- Test migrations on staging before production.
- Keep the prior application image and a recovery plan for each deployment.

## 12. Security and operational controls

- Hash passwords with Argon2id in the application; never store plaintext passwords.
- Store only hashes of session, invitation, verification and reset tokens.
- Enforce tenant authorization in every backend repository/service.
- Keep sensitive bank details and private customer information out of public website media.
- Use parameterized SQL and bind variables.
- Never expose database credentials, wallets or private object storage credentials to the browser.
- Use a restricted runtime database account.
- Log privileged actions in `AUDIT_LOGS`.
- Do not log passwords, token values, session IDs, wallet contents or payment secrets.
- Restrict access to audit and financial records.
- Use soft status changes rather than destructive deletes for business records.
- Retain booking and payment history according to an approved data-retention policy.

## 13. Required validation tests

### Schema and referential integrity

- All tables, constraints and indexes create successfully on the target Oracle ATP release.
- Every tenant-owned FK includes tenant identity where required.
- Cross-tenant business/resource/booking relationships fail at the database layer.
- Parent rows cannot be deleted when retained child history exists.

### Tenant isolation

- Tenant A cannot query Tenant B's business, locations, resources, customers, bookings, payments, staff, website settings or reports.
- A user with memberships in two tenants receives only the currently selected authorized tenant context.
- Branch assignments are enforced for staff.

### Booking concurrency

- Two simultaneous requests for the same resource and overlapping time cannot both reserve the same 15-minute slot.
- A failed multi-slot insert rolls back all slot rows.
- Expired holds release all associated slots.
- A hold conversion leaves no gap in reservation protection.
- Manual and online booking use the same reservation service.
- Cancellation releases the correct slots and preserves history.
- Maintenance block creation is serialized against booking operations.

### Financial integrity

- Multiple payment receipts calculate payment summary correctly.
- Voided receipts are excluded from collected totals.
- Refund totals cannot exceed net receipts.
- Subscription payments cannot be confused with venue payments.
- Historical price snapshots remain unchanged after pricing updates.

### Operational

- Worker claims jobs safely using row locking / `SKIP LOCKED` where implemented.
- Duplicate idempotency keys return the stored result.
- Outbox events can be retried without duplicate external effects.
- Migration rollback or forward-recovery procedures are tested.

## 14. Known limitations and production gates

1. The DDL has been statically reviewed for table ordering, named constraint/index uniqueness and composite foreign-key target keys. It has **not** been executed against the user's live Oracle Autonomous Database. Actual execution and integration testing on the selected ADB version are mandatory before production.
2. The 15-minute interval is enforced as the MVP reservation grid. Supporting different slot intervals later requires a deliberate migration and revised slot-generation logic.
3. Pricing-rule overlap, cross-row booking totals, refund totals, payment summary recalculation and maintenance-versus-booking conflicts are service-layer transaction invariants, not all expressible as simple row-level constraints.
4. Oracle VPD policies are not included in the bootstrap script; add them only after pooled-session context handling is tested.
5. The Always Free Autonomous Database does not provide the same managed backup and point-in-time recovery capabilities as paid production configurations. A suitable backup and disaster-recovery solution is a commercial production gate.
6. Marketplace, recurring bookings, online payment gateway and custom-domain features have future-ready tables but are not part of the first MVP implementation.
