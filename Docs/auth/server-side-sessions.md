# Server-side dashboard sessions

The API generates 32 random bytes, sends the canonical base64url value in a host-only HttpOnly cookie, and stores its SHA-256 digest in Oracle. The view filters unrevoked rows to the `DASHBOARD` audience. The session carries no active tenant or membership IDs. The guard rechecks the live session, account and membership eligibility on each request. Revocation uses Oracle directly and no in-process cache. [Session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

The database sets the absolute expiry and initial idle deadline using the UTC session clock. The browser's absolute expiry comes from the installed row. If the last activity is old enough, a conditional update advances idle expiry to the earlier of the new idle deadline and absolute expiry. It requires both persisted deadlines to remain live and the row to remain unrevoked. A competing touch or revocation triggers a fresh read when the update changes zero rows. Idle tracking writes are coalesced by the configured minimum touch interval. The source limiter uses its own Oracle window counters. Legacy rows with no idle deadline cannot authenticate through the Step 12 dashboard routes.

## Policy and storage

The approved configurable defaults are 12 hours absolute, 30 minutes idle and a minimum one-minute gap between persisted activity touches. `AUTH_SESSION_ABSOLUTE_SECONDS`, `AUTH_SESSION_IDLE_SECONDS` and `AUTH_SESSION_TOUCH_SECONDS` allow overrides with 60 seconds ≤ touch < idle ≤ absolute. Separate devices keep independent sessions. There is no remember-me option. The isolated Oracle harness uses the approved defaults. [Approval](../planning/decision-register.md#d-33--step-12-policy-approval-and-isolated-oracle-verification)

Migration `000028_account_sessions` adds nullable `IDLE_EXPIRES_AT_UTC` and `REVOKE_REASON` so previous records and migrations remain intact. The allowed reasons are `LOGOUT`, `ROTATED` and `PASSWORD_RESET`. No source IP, user agent or bearer is added to the session/audit row. The API holds only read and column-scoped write grants through the dashboard view and a separate revocation view. The latter exposes IDs and revocation fields across audiences because reset invalidates all existing sessions. Both views hide revoked rows. [Migration](../../database/migrations/000028_account_sessions) · [Grant matrix](../../database/provisioning/step12-runtime-grants.mjs)

Login, logout and password reset serialize on the same user row. A login that verifies the old credential can commit before reset and have its session revoked, or can acquire the lock after reset and fail the credential recheck. Session touch can neither revive revoked state nor exceed the absolute deadline. An interrupted commit may have an uncertain outcome and is never retried automatically. [Oracle driver's transaction handling](https://node-oracledb.readthedocs.io/en/v26.0.0/user_guide/txn_management.html)
