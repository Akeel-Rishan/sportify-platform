## Proposed contracts and controls

- Use the documented POST paths `/api/v1/auth/register`, `/api/v1/auth/verify-email` and `/api/v1/auth/verification/resend`. Reject unknown fields, tenant and role IDs, permission lists and platform status. Reuse the API envelope and request ID. Use a generic `accepted` response for valid registration or resend submissions, a minimal `verified` response on success, and one safe error for unusable links.
- Trim and lowercase supported ASCII email addresses for the unique lookup. Preserve an appropriate display address and avoid provider-specific alias rewriting. Validate mobile numbers in E.164 syntax.
- Propose 15–128 Unicode code points and a 512-byte UTF-8 bound for passwords. Do not alter them through case conversion, trimming, normalization or truncation. Evaluate a compromised-password blocklist and bound concurrent hashing before enabling a public route. Use library-generated salts and Argon2id with at least 19 MiB, two iterations and parallelism one. Benchmark values on the target runtime, including ARM64 before claiming platform execution. Do expensive hashing outside Oracle transactions. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) · [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- Propose a 60-minute link lifetime, 60-second resend cooldown and up to three issuance events per account in a rolling 15-minute window, including initial registration. Enforce account limits durably across API instances. Require approved per-source limits on verification attempts and issuance. Read the socket peer until a specific trusted proxy boundary is configured. Source rate limits can return a safe `429`. Account suppression keeps the generic acknowledgement and leaves confirmation available for a valid link. [OWASP recovery token guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
- The mailbox holder supplies the final password in the explicit confirmation POST. A pending password chosen by someone who mistyped or used another person's address cannot become an active credential merely because the recipient follows the link. A future link landing page must avoid a state-changing GET and keep the bearer out of routine logs, referrers and third-party assets.

Candidate dependency `argon2@0.44.0` documents support for Node.js 18 and later and prebuilt Linux ARM64 targets. Confirm the binary on the project's Node.js runtime and the actual deployment image before selecting the pin. The existing NestJS strict DTO pipe can enforce bounded input with a route-specific schema. [node-argon2 0.44.0](https://github.com/ranisalt/node-argon2/blob/v0.44.0/README.md) · [NestJS validation](https://docs.nestjs.com/techniques/validation)

The proposed default creates an active `BUSINESS_OWNER` role plus inactive `BUSINESS_MANAGER` and `RECEPTIONIST` defaults with no assignments or permission mappings. Review staff mappings when the staff authorization flow is defined. Proposed explicit owner permissions are `business.read`, `business.manage`, `location.read`, `location.manage`, `resource.read`, `resource.manage`, `booking.read`, `booking.create`, `booking.cancel`, `booking.manage`, `payment.read`, `payment.record`, `payment.refund`, `staff.manage`, `report.read`, `website.manage`, `subscription.read`, `customer.read` and `customer.manage`. New catalog entries would require a deliberate mapping change. [Current reference codes](../../database/seeds/000011_tenant_permissions/001_permissions.sql)

## Oracle transition and delivery design

1. Registration writes the pending account, verification record and safe audit/outbox references in one transaction. Resolve simultaneous registrations via `UQ_USERS_EMAIL_NORMALIZED`. Treat only that expected conflict as a duplicate and surface unrelated failures through the existing safe error path.
2. Issue and confirm links under a consistent user-then-token lock order. Recheck pending account, exact token digest, key version, expiry, consumption and revocation under lock. Use Oracle's UTC session clock. Resend atomically revokes prior live links when issuing a replacement. Verify concurrently with resend in integration tests.
3. In the confirmation transaction, consume the token, store the mailbox holder's encoded password, verify and activate the user, create the tenant and its membership and roles, then record a scoped audit event. A failure rolls back the entire transition. The existing `TENANTS.STATUS` constraint accepts `TRIAL`, `ACTIVE`, `SUSPENDED` and `CLOSED` and defaults to `TRIAL`. The proposed `PENDING_ONBOARDING` value requires a narrow forward migration and an explicit insert. Commercial activation and business/location creation belong to their own flows. [Tenant table migration](../../database/migrations/000004_security_roots/001_tenants.sql)
4. Use only the approved email purpose with a versioned external HMAC-SHA-256 key and canonical immutable record inputs, including a random public ID, user binding and expiry. Persist the SHA-256 digest, public ID, key version and lifecycle state. Reconstruct the bearer transiently at send time after rechecking that the record remains eligible. The payload needs only a record reference and key version. Send after commit. Use a fixed configured HTTPS link origin. Retain older key versions only for the approved delivery and expiry window. [Token table migration](../../database/migrations/000007_sessions_and_tokens/002_email_verification_tokens.sql) · [Operational secret design](../database/operational-data.md)
5. Reuse the shared Oracle transaction callback and exact string identifiers. Scope runtime grants to the specific tables, columns and operations demonstrated by each API or delivery path. Keep migration history, unrelated objects and audit mutation outside runtime access. Confirm actual grants on a designated disposable schema. [Connection and transaction rules](../database/connection-pooling.md) · [Account model](../database/account-and-privilege-model.md)
