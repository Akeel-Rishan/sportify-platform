## Registration race investigation

Signup normalizes the email and attempts the user insert before token, outbox and audit writes. `UQ_USERS_EMAIL_NORMALIZED` is the concurrency authority. The service accepts only `ORA-00001` for that exact owner and constraint as the duplicate case. The losing callback returns before writing the other records. Every other error follows the normal rollback path. The pool commits successful transactions, rolls back failures and releases the connection in `finally`. It drops a connection if rollback fails. Acquisition and per-call timeouts remain bounded. [Signup transaction](../../apps/api/src/modules/auth/registration.service.ts) · [Connection lifecycle](../../packages/database/src/pool.ts) · [Oracle uniqueness error](https://docs.oracle.com/en/error-help/db/ora-00001/index.html?r=23ai) · [Driver pool counters](https://node-oracledb.readthedocs.io/en/v26.0.0/api_manual/pool.html)

The original evidence showed one synthetic signup committed and an unexpected HTTP result from the racing request. The trace did not include the failing status, an Oracle/driver error, or a connection-scope error sufficient to explain it. The separate audit-denial assertion and reserved bind-name defects were diagnosed and corrected earlier. Neither establishes the cause of the later signup race. The rollback-only probe at the time established that a single registration could complete its writes, with its transaction then discarded. [Original live record](registration.md#verification-record)

The review harness places barriers immediately before the competing user inserts and confirmation row locks, on distinct Oracle session IDs. The resend race holds confirmation between its eligible token read and its locking transaction, then lets resend commit the replacement first. The harness checks the exact unique constraint, both public statuses, pending-account, token and outbox counts, scope-level errors, borrowed connections and full cleanup. Session IDs, addresses, bearer values and raw SQL error messages are omitted from diagnostics. Each resume verifies the exact 27-migration catalog, an empty fixture baseline and zero temporary grants before writing. [Live harness](../../database/tests/oracle-step11.mjs)

**Three independent, consecutive live runs passed on 28 November 2026.** All six parallel signup requests returned `202`. Each pair hit the canonical unique constraint exactly once, committed one pending account, issued one token, and wrote one outbox event. Each run passed the competing confirmation and resend cases, restricted-runtime checks and the deliberately injected rollback. Both pools had zero borrowed connections at the assertion points, with zero unexpected database errors. Each run closed the pools and verified zero fixture rows or temporary grants. The test retains the 27-migration ledger. Barriers allow 10 seconds, HTTP requests 20 seconds, and runtime Oracle acquisition and call budgets remain 5 seconds each. The earlier failure did not recur and its specific cause remains unconfirmed. [Redacted run evidence](evidence/step11-concurrency-redacted.json)

## Final verification

The three live runs used the existing protected credentials for the disposable owner and the actual restricted API and worker identities. They verified the catalog, no-op migration repeat and runtime access limits on every run. The application baseline had 26 migrations when those isolated runs ended. The first 26 manifest entries and their 239 SQL and seed files matched the Git checkpoint byte for byte. The configured-secret and private-file scan found zero matches. Local registration settings remain disabled.

The closure pass reran lint, strict type checking, all 226 unit and HTTP tests and production builds. Line coverage was 91.98% overall and 90.90% for the API auth module. The review changes are confined to the test harness, documentation and redacted evidence. [Registration verification record](registration.md#verification-record)
