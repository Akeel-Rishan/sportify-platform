# Verification token delivery

Registration and eligible resends insert the token record and its outbox intent in one Oracle transaction. A resend locks the pending user, checks the rolling account limit and cooldown, revokes eligible older links and commits a replacement. Confirmation takes the same user lock before rechecking and consuming the token. The Oracle UTC clock determines expiry. Each link lasts 60 minutes and has one successful consumption.

The token is a 32-byte HMAC-SHA-256 output, encoded as canonical base64url. The canonical, versioned input binds the purpose, key version, random token public UUID, user public UUID and UTC expiry. Oracle stores SHA-256 of the encoded bearer. Outbox event `auth.email-verification.requested` carries only `{ tokenId, keyVersion }`. The worker-facing adapter checks eligibility through `VW_AUTH_VERIFICATION_MAIL`, which projects pending and unexpired verification records. It checks the reconstructed digest and calls the configured transport outside the Oracle transaction. The evidence callback receives a fixed outcome such as `sent`, `ineligible` or `delivery_failed`.

The adapter uses a configured HTTPS origin and a URL fragment. The future frontend captures and removes the fragment from the address bar, avoids analytics and third-party assets on the landing page, uses `Referrer-Policy: no-referrer`, asks the user to confirm the profile and password, and submits an explicit POST. Scanners can follow the link without consuming it. Express logs matched route names, request IDs and status only. Delivery callbacks and transport errors must avoid including recipient data, link URLs or credentials.

## Dispatch and key operations

The web/API workflow creates durable delivery intent. The separate worker-side adapter is the consumer boundary for the future fenced dispatcher. The current worker startup does not poll jobs and no provider or inbox is configured. A dispatcher can supply a committed reference, `SPORTIFY_WORKER` database pool, provisioned keyring, validated frontend origin, transport callback and redacted evidence callback. Respect the abort signal and retry budget. Recheck before every attempt. A race after the final eligibility read can send an old link, which Oracle will refuse. A retry may deliver the same link twice but cannot create an extra account or tenant transition.

- Generate each key independently from 32 random bytes. Inject a version-to-base64url key map into the API issuer and authorized delivery process from a protected secret store. Use a different key for source counters.
- Rotate in stages. Make both processes recognize the new version before switching the API issuance version. Keep all live worker versions through the old links' final expiry and eligible dispatch window. Remove the retired key from both processes and the secret store thereafter, subject to approved key management.
- For compromise, remove the affected version from accepted API and delivery keys and activate a new version. Inspect and revoke still-live affected rows through reviewed owner operations. Eligible pending owners can request a replacement. Avoid copying raw tokens, URLs, keys or request bodies into incident records.

Provider acceptance and inbox delivery require their own evidence. The local sink exercises transport and link reconstruction with synthetic addresses. [Account-scoped operating decisions](../planning/decision-register.md#d-30--step-11-registration-and-email-verification)
